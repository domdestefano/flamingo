# Button

Buttons trigger an action or a change of state. Use them for the primary
things a rider can do on a screen, not for navigation between screens.

## Usage

Use a button when the rider is committing to an action: accepting an order,
confirming a delivery, submitting a form. Reserve the **primary** variant for
the single most important action on a screen.

### Do

- Use one primary button per screen so the main action is unambiguous.
- Write labels as an action plus its object: "Accept order", not "OK".
- Keep the primary action visible without scrolling on the screens where it
  matters most (order acceptance, delivery confirmation).

### Don't

- Don't stack multiple primary buttons — it removes the visual hierarchy that
  tells the rider what to do first.
- Don't use a button for navigation; use a link.
- Don't rely on colour alone to signal state — pair it with a label change.

## Variants

| Variant   | When to use                                             |
| --------- | ------------------------------------------------------- |
| Primary   | The single most important action on the screen.         |
| Secondary | A supporting action shown alongside a primary action.   |
| Ghost     | Low-emphasis actions, e.g. inside a dense list row.     |

## Accessibility

- Every button needs a discernible label; icon-only buttons require an
  accessible name.
- Ensure a visible focus state (inherited from Flamingo tokens) is never
  removed in overrides.
- Minimum touch target is 44×44px — relevant on the rider app's smaller
  screens and gloved-hand usage.
