## Interactions

### Refreshing with no content

When the user drags down to refresh the content, the pull to refresh UI element starts from where
the header right below the bottom margin of the header, until it's width (as a 1:1 or 1.5x
ratio). As the pull to refresh UI element emerges from beneath the header, it starts to scale up
to reach the original size (48x48px), until it reaches the storage margin at the top of the
screen. After that point, the size remains 48x48px, and the user can drag it down or lose to
frictions of having its margin on the top of the header of 48px. The spinner starts rotating only
after the user has dragged the trigger pull point.

When loading is finished, or if an error occurs, the component goes back to its starting point.

### Refreshing with content

When refreshing with content in the interface, everything is the same as the refreshing with no
content interaction. The only difference is that when dragging and while the spinner is rotating,
the content, the pull to refresh UI elements refers to, is pushed down to show the interaction
without abstractions.

### Refreshing with a complex Header

The pull to refresh UI element emerges from below the Header. If the header is complex, meaning
that there are other elements attached to it, like a name or date selector, or a tab-bar, the
pull to refresh UI elements emerge from beneath the whole header.

## Guidelines

### Description

The pull-to-refresh or swipe-to-refresh UI element lets a user pull down on a list of data being
viewed in order to retrieve more data or refresh the UI. The refresh indicator uses **only in
conjunction with a refresh gesture** or action.

Pull to refresh works well for lists and card collections where content is updated frequently, or
when the collection usually requires constantly-updating stream of items, and the pull to refresh
gives the user the impression that new content will always appear when refreshing the UI. It's
safety mechanism because it's loading even preserves the loading of new content, the user can
pull to refresh to restart the loading process.

Appropriate use cases for pull-to-refresh are:

- Content feeds
- Inbox messages

### Refresh time

The user won't take time to become aware of what they keep the timeline of an action.
Immediately, the system should give some visual feedback that it has received the request. The
system's confidence in the refresh happened already needs to be at a representable timeframe.
This engages the user and prevents confusion.

### Placement

The pull to refresh UI element emerges from below the Header. If the header is complex, meaning
that there are other elements attached to it, like a name or date selector, or a tab-bar, the
pull to refresh UI elements emerge from beneath the whole header.

### Pull to refresh vs. loading bar

Pull to refresh uses a manual gesture triggered by the user to force the loading of new and
updated content. Loading bars, instead, are used when the loading is triggered by an action
performed by the system (not the user), for content different from a manual gesture.
