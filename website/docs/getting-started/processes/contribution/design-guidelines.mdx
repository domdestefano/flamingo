## Design guidelines for component proposals

To create a well defined **proposal** for a new component or a component change please follow
these guidelines as much as possible:

| Area | Guideline |
| --- | --- |
| Use cases | Research on all the use cases your component **needs** to cover. Consider what edge cases might appear. Define different types (e.g. _Default, Alert, Error, ..._). |
| (Re-) sizing / Responsiveness | Consider sizing of component: Min./Max width & height, behaviour in different. |
| Visual alignment | Ensure your component proposal uses Flamingo tokens and fits the overall look and feel within the system. |
| Accessibility | Ensure that the design meets accessibility standards, such as contrast ratios, and proper semantic structure. |
| Content | Use placeholders for labels. Consider how they might be impacted in different languages. Verify that all images and media are high-quality, optimised, and relevant if any. |
| Scalability | User teams should be able to reuse it. Keep it scalable and abstract enough. |
| (Micro) Animation | Consider how your component should behave when being interacted with (e.g. hover animation). Refer to the [animations settings](/getting-started/processes/asset-creation-and-implementation/animations) when proposing easing functions and duration settings. |

:::info Bad with visual design?
No worries at all! Explain as good as you can your desired component/change and the Flamingo
designers will create it.
:::
